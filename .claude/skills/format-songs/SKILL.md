# Format songs for the catalog

Turn messy lyrics into clean, slide-sized sections and add them to
`local/song-catalog.json` as new songs. The catalog and the source lyrics are
local-only: `local/` is gitignored, and the source file (usually `songs.md` at
the repo root) must stay untracked. Never commit either.

## Catalog shape

Defined in `src/types/songs.ts`. Top level is
`{ format: "rhema-song-catalog", version: 1, exportedAt, songs: Song[] }`.
Each song:

- `id`, `createdAt`, `updatedAt`: generated by the helper script.
- `title`, `artist`: `artist` is `""` for traditional or unknown songs. Credit
  featured singers as `"Elevation Worship (feat. Tiffany Hudson)"`.
- `ccliNumber`: optional; include only when the source gives one.
- `sections`: `{ id, label, lines[] }`, each **unique** lyric section exactly once.
- `arrangement`: section ids in the order the song is sung. Repeats point at
  the same id again. The app shows back-to-back repeats as "Chorus (x2)".
- `linesPerBlock`: `0` (never auto-split), matching the rest of the catalog.

## Cleaning rules

1. **Labels.** Use `Verse 1`, `Verse 2`, …, `Pre-Chorus`, `Chorus`, `Bridge`,
   `Interlude`, `Tag`, `Outro`, `Intro`. Number a label only when there are
   different sections of that kind (`Bridge 1`, `Bridge 2`). A single chorus
   is just `Chorus`.
2. **Define each section once.** A chorus sung four times is one `Chorus`
   section that shows up four times in `arrangement`, never four copies. Only
   create `Chorus 2` when the **words differ** (for example "bow down" vs.
   "clap, clap").
3. **Fit a slide.** Aim for 2–4 lines per section, 6 at most. Split long
   sections into numbered parts (`Bridge 1`…`Bridge 4`) and break very long
   lines into short singable ones.
4. **Strip non-lyrics.** Remove singer or part annotations ("[Tiffany]",
   "(Men)"), spoken ministry or exhortation, vocal ad-libs ("Aye ye ye",
   "oh-oh-oh" fillers), and repeat markers ("x3", "Repeat"). Keep a short
   echo line in parentheses only if the congregation sings it.
5. **Fix text.** Correct obvious misspellings ("exhalt" → "exalt"). Use
   sentence case per line, capitalise pronouns for God (You, Your, Him, He)
   to match the catalog, and drop trailing punctuation except `?` and `!`.
6. **Live transcripts.** Find the core repeating sections and drop the
   improvised material. Mention anything substantial you left out.
7. **Duplicates.** Check the catalog for the same title and artist first. A
   similar title by a different artist is a different song, so add it, but
   say so.

## Arrangement rules (order is important)

The arrangement must follow how the **song is designed**: every repeat
appears in order, each time it is sung.

- **Hymns.** Each stanza is its own section (`Verse 1`…`Verse N`). The
  refrain comes after every verse:
  `Verse 1, Chorus, Verse 2, Chorus, Verse 3, Chorus, Verse 4, Chorus`.
  Never list the verses and then a single chorus at the end.
- **Modern songs** follow the same rule. If the song goes
  `Verse 1, Pre-Chorus, Chorus, Verse 2, Pre-Chorus, Chorus, Bridge, Chorus`,
  the arrangement lists all of that, including the repeated pre-chorus and
  every return of the chorus.
- **Back-to-back repeats.** When the song itself sings a section twice in a
  row (chorus sung twice before the bridge), list it twice
  (`Chorus, Chorus`). The app shows it as "Chorus (x2)".
- **Live recordings.** Follow the song's normal structure, not every
  extended worship-leader loop. Keep a structural repeat (the final chorus
  sung twice); drop a fifth improvised run of the tag.
- **Unclear structure.** If the source doesn't show the order, use the
  standard structure for that kind of song. Never leave `arrangement` empty
  when a section repeats, because empty means "authored order, each section
  once".

## Workflow

1. Read the source lyrics. If the user names no file, look for `songs.md` at
   the repo root. Make sure it is gitignored (`git check-ignore -v songs.md`).
   If it isn't, add it to `.gitignore`.
2. Write a draft JSON array to the scratchpad. Sections are written by label,
   and the arrangement is a list of labels:

   ```json
   [
     {
       "title": "Amazing Grace",
       "artist": "John Newton",
       "sections": [
         { "label": "Verse 1", "lines": ["Amazing grace, how sweet the sound", "That saved a wretch like me"] },
         { "label": "Chorus", "lines": ["..."] }
       ],
       "arrangement": ["Verse 1", "Chorus", "Verse 2", "Chorus"]
     }
   ]
   ```

3. Dry-run, then apply:

   ```sh
   bun .claude/skills/format-songs/add-songs.ts <draft.json>          # validate + preview
   bun .claude/skills/format-songs/add-songs.ts <draft.json> --write  # back up + append
   ```

   The script checks that labels are unique, every arrangement label exists,
   every section is used, and no line is empty. It also rejects a song whose
   title and artist already exist (pass `--allow-duplicate` to override). It
   prints each arrangement the way the app will collapse it. With `--write`,
   it saves a timestamped backup next to the catalog, appends the songs, and
   writes `local/new-songs-<timestamp>.json`, a catalog export holding only
   the new songs.
4. Report each song briefly: sections created, arrangement, and what was
   dropped or corrected. Give the backup path.
5. The app doesn't read `local/song-catalog.json` live; it's an export.
   Songs get into the app through the Songs catalog's import, which **adds
   every song in the file** with fresh ids. Tell the user to import the
   `new-songs-*.json` file, not the full catalog, or every existing song will
   be duplicated.
